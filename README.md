# Blueprints

Linted, living reference architectures for agentic systems.

A self-contained app of the naveenlabs AI galaxy (siblings: Trust, Radar). Clone it, install, run: nothing else is needed. Blueprints reads Trust's tool grades and Radar's framework facts from their published data (`TRUST_DATA_ROOT`, `RADAR_DATA_ROOT`); with none present it still works and shows its empty states.
Design: `docs/design.md` (one design for all three apps; this one implements §4 (core) and §7 (Blueprints)).
Architecture, security, reliability and operations: [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md).

Production at a glance: a hardened web container (non-root, read-only image, no Linux capabilities, CPU and memory
limits) with a Docker health check on `/healthz` (which opens the database); HSTS, a strict CSP and a permissions
policy on every response; exact dependency pins in `requirements.txt`.

## Local development (Windows)

```powershell
python -m venv .venv
.venv\Scripts\python -m pip install -r requirements-dev.txt
.venv\Scripts\python -m pytest -q
```

Run the web app (Chrome and Edge resolve `*.localhost` to 127.0.0.1):

```powershell
$env:PUBLIC_SCHEME="http"; $env:PUBLIC_PORT=":8002"; $env:ADMIN_USER="owner"; $env:ADMIN_PASSWORD="local-dev-password-123"
.venv\Scripts\python -m uvicorn web.app:build --factory --port 8002
```

Open http://blueprints.localhost:8002 and http://blueprints.localhost:8002/admin. Only this app's host answers; any other host is a 404.

Run the worker (uses the laptop's Claude Code login and Ollama):

```powershell
$env:PLANET_MODULES="blueprints.jobs"; $env:WEIGHTS="blueprints=100"
.venv\Scripts\python -m core.worker
```

## Blueprints engine

With `blueprints.jobs` in `PLANET_MODULES` the worker seeds the four hand-written blueprints, reacts to Trust grade
changes and Radar breaking-change events (flagging affected blueprints and queueing a regeneration; with separate apps it notices the same changes by comparing Trust's and Radar's published data with what it saw last time, read from `TRUST_DATA_ROOT` and `RADAR_DATA_ROOT`), publishes approved
blueprints every 30 minutes, and generates one new blueprint per night from `blueprints/briefs.json` (Claude, night
window). Every generated blueprint waits in `/admin` as a `blueprint_approval` item; only approved ones are published,
and a draft that still fails the linter after two revisions is stored as rejected.

```powershell
.venv\Scripts\python -m blueprints.cli seed
.venv\Scripts\python -m blueprints.cli lint path\to\blueprint.json
.venv\Scripts\python -m blueprints.cli generate research-agent
.venv\Scripts\python -m blueprints.cli publish --data-root data\published
```

Prices live in `blueprints/pricing.json` with their source and date (flagged stale after 45 days). Pattern catalog
entries are drafts until you mark them `reviewed`. Quality gate: `.venv\Scripts\python -m evals.blueprints_eval`. The linter also warns (never blocks) about a tool with no `tool_ref` and about prices, versions, years or grades written into free text.
The Blueprints pages are described below.

## Blueprints site

`blueprints.localhost` serves the published library: `/` (filter by use case, risk, topology), `/b/<id>` (why-trace,
components with Trust grades, failure modes, threats, eval plan, cost with a volume slider and a token slider),
`/patterns` and `/finder`. Everything reads the verified `blueprints/library` release; a blueprint that fails
today's linter, has a refresh queued or is priced from a stale table is shown with a banner, never hidden.

- `POST /api/lint-blueprint`: body is a blueprint or `{"blueprint": ...}` (200 KB max). Returns `lint`, and when the
  schema is valid `decision` and `cost`. It lints against the published Trust grades and Radar packages. Rate limited.
- `POST /api/finder` takes a requirements profile and returns the decided topology, its why-trace, mandatory controls and
  the nearest blueprints; `notes` is a short local-model adaptation note and is `null` when Ollama is busy or down.
  `POST /api/finder/prefill` turns a description into form fields for the user to confirm (503 when the model is busy).
- `/admin` shows a preview of every draft (`/admin/blueprints/<id>/<version>`: linter today, why-trace, cost, diagram
  source, approve or reject) and lists approvals the linter currently holds.

- `/compare`: two published blueprints side by side; rows that differ are highlighted.
- "Runnable starter" on each detail page: a LangGraph skeleton generated by code from the blueprint, pinned to the version Radar has an API snapshot for, and offered only when every LangGraph symbol it uses exists in Radar's published `surface.json` (`starter = true` in `radar/sources.toml` picks the package). It runs offline (model calls are stubs); downloads are `/b/<id>/starter/app.py`, `requirements.txt` and `README.md`. Without Radar data the page says why there is no starter.
- `/custom`: bring your own key. The browser calls api.anthropic.com with your key (never sent to this site, never stored); `POST /api/custom/prompt` builds the prompt and `POST /api/custom/check` restores the forced fields (id, profile, version, changelog) and judges the draft with the same linter, decision rules and cost model. Up to two automatic revisions. Nothing is saved or published.

Local preview (seeds only, no model):

```
.venv\Scripts\python -m blueprints.cli seed --db data/blueprints.db --data-root data/blueprints-published
.venv\Scripts\python -m blueprints.cli publish --no-llm --db data/blueprints.db --data-root data/blueprints-published
$env:DB_PATH="data/blueprints.db"; $env:DATA_ROOT="data/blueprints-published"
.venv\Scripts\python -m uvicorn web.app:build --factory --port 8002
```
then open http://blueprints.localhost:8002/.

- **Look:** Blueprints has its own theme pack in `web/static/themes/blueprints/` (design canvas: dotted canvas, Manrope,
  violet accent, light by default). The home is a gallery of canvas cards with the library filters in the hero; each
  blueprint page draws its flow as node cards on a canvas.

## Deploy (VPS)

1. DNS A record `blueprints` pointing at the VPS IP; Traefik runs on the VPS.
2. The naveenlabs-ai stack is running (it provides the `naveenlabs-ai_default` network and `ollama`); give its `ollama` service a memory limit (for example `mem_limit: 4g`) so it cannot crowd out other apps.
3. `cp .env.example .env`, `cp batch.env.example batch.env`; set `ADMIN_PASSWORD` (16+ characters; `/admin` stays disabled while it is the default or short); on the laptop run `claude setup-token` and paste the token into `batch.env`.
4. `docker compose up -d --build`; Traefik picks up the labels and issues the certificate. Wait for `docker inspect -f '{{.State.Health.Status}}' blueprints-web-1` to say `healthy`.
5. Monitoring: probe `https://<host>/healthz` from outside the server (the `atlas` repository's `uptime` workflow does this every 30 minutes); optionally an Uptime Kuma push monitor whose URL goes in `KUMA_PUSH_URL`.
6. Optional: `docker compose -f docker-compose.yml -f docker-compose.siblings.yml up -d` mounts the Trust and Radar apps' data volumes read-only.

## The shared core

`core/` (LLM gateway, job engine, publishing, events, review queue, scheduler) and the shared web kit (`web/app.py`, `web/admin.py`, `web/config.py`, base templates and stylesheet, and their tests) are identical copies of the master in the `atlas` repository, so this repository runs on its own. The list is `scripts/core_manifest.json`; `CORE_VERSION` names the master commit last synced.

```powershell
python scripts/sync_core.py --source PATH_OR_GIT_URL --check    # what differs from the master
python scripts/sync_core.py --source PATH_OR_GIT_URL            # pull the master's core into this repo
```

A change to the shared core belongs in the master first, then in each app repo with this script.
