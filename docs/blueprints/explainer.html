How Blueprints is built

Blueprints is a library of reference architectures for AI agents, each one linted, priced and kept up to date as the tools it relies on change. Its Architect agent turns a plain-words description into a checked, priced design: models write the drafts, and code decides whether they pass.

The system

Two containers, one database, and two optional neighbours

blueprints-web serves the library, the lint and Finder APIs, and runs the Architect agent on background threads. blueprints-batch runs the durable job worker: generation, publishing and reactions to tool and package changes. Trust's grades and Radar's package data are mounted read-only; without them Blueprints still works.

  • blueprints-web library, APIs, Architect; read-only image
  • blueprints-batch leased jobs, cached stages, backoff, dead-letter
  • SQLite (WAL) drafts, approvals, Architect runs, settings
  • Published library immutable releases with a SHA-256 manifest
  • OpenRouter Architect models; nightly drafts under a daily cap
  • Trust + Radar data tool grades and package APIs, read-only
  • Ollama optional; writes Finder's short adaptation note

The rule behind every design choice

Models draft, code decides

A model may turn a description into a requirements profile, draft a design, write the decision record, fix what the checks found and review the result. The topology, the mandatory controls, every lint verdict, every cost and latency number and the decision to publish are plain code, so a fluent draft cannot talk its way past them.

What a model writes

  • The profile behind the visitor's words
  • The design, the decision record, the runbook
  • Fixes for problems the checks list
  • One review that scores and attacks the design

What code decides

  • Topology and mandatory controls: 19 decision rules
  • Pass or fail: 24 lint rules, 7 consistency rules
  • Cost, latency and capacity at 1x, 10x, 100x
  • Which questions to ask; what gets published
blueprints/cost.py (shortened)
"""The model never produces a number; an unpriced model makes the estimate incomplete instead of guessing.""" usd = (step["input_tokens"] * price["input_per_mtok"] + step["output_tokens"] * price["output_per_mtok"]) / 1e6 * calls seconds = (price["ttft_s"] + out_tokens / price["tokens_per_s"]) * calls monthly = per_request * volume * 30
WhyReviewers, interviewers and visitors can check every number by hand. A model can still write a weak design, but it cannot publish one, price one or pick its own topology.
The decision engine

Same 19 rules, five real profiles

One row per real requirements profile: the four published blueprints and the Architect's online-shop design. A column is a topology. Code rules some topologies out (outline only), keeps the allowed ones (low tiles) and picks one (the violet pillar, named by the rule that chose it).

  • Interactive latency leaves only workflow or router: no loops
  • High risk never allows the autonomous topology
  • Open-ended and parallel work gets orchestrator and workers
  • Several request kinds are split by a router
  • Mandatory controls come from the same profile: PII adds an input filter and an audit log

One linter, everywhere

24 rules a design must pass, wherever it comes from

The same lint() function checks hand-written seeds, nightly drafts, the Architect's designs, custom blueprints and anything posted to /api/lint-blueprint. Errors block approval and publishing; warnings are shown.

RuleWhat it enforces
unmitigated-capabilityWrite, exec, network or payment on a component needs a control
missing-mandatoryEvery control the decision engine requires is present
forbidden-topologyOnly a topology the rules allow for this profile
gate-not-wiredWhen a human gate is required, every acting capability goes through it
unknown-modelModels must be in the priced table, so cost is never invented
tool-not-eligibleA referenced tool needs a Trust grade of A or B
unknown-frameworkA framework must be a package Radar tracks
volatile-fact-in-textNo prices, versions, years or grades in free text (warning)
blueprints/linter.py
VOLATILE = re.compile( r"\$\s?\d|\b\d+\.\d+\.\d+\b|\b(?:19|20)\d{2}\b|\bgrade\s+[A-F]\b", re.I) # prices, versions, years and grades go stale: # they belong in the dated tables, not in prose

The public lint API

Lint, decision and cost for any blueprint JSON. Bodies over 200 KB are refused, and the rate limit is spent before validation, so malformed requests are not free. NaN and oversized numbers are refused.

Living context

Grades and tracked packages come from Trust's and Radar's published data at lint time, so a tool that drops below B fails a blueprint that was clean yesterday.

Stated assumptions

Token counts are estimates, not measurements; steps run one after another, so parallel branches overstate latency; time to first token and output speed are assumed per model; 30 days a month. A price table older than 45 days is flagged stale.

Living links

A Trust grade change or a Radar breaking change raises an event; batch flags every blueprint that uses that tool or package and queues a refresh. A stale entry gets a banner, never hidden.

The Architect agent

Nine nodes, four of them a model

A LangGraph state graph. Decide, ground, capacity, check and finish are code; draft, record, fix and review use a model. Check and fix loop until the linter and the consistency rules are clean (up to 4 rounds); one review, which also attacks the design, can send it back (up to 3 rounds).

  • decide 19 rules pick the topology and controls
  • ground 2 nearest published blueprints, patterns, allowed models
  • draft one design on the chosen topology
  • capacity cost and load at 1x, 10x, 100x
  • record decision record, runbook, a cheaper variant
  • check 24 lint + 7 consistency rules
  • review 8 scored areas + red team

One sentence in, a profile and a topology out

The check-and-fix loop

The draft must agree with itself

The shop design ends with 5 components and 7 guardrails. After each draft or fix, code runs the linter and 7 consistency rules over the design and its decision record. Each problem goes back to the model with its path; the model returns only the parts it changed.

blueprints/architect/consistency.py: the 7 record rules
The p95 latency target is at least the computed flow latency
Every open risk and runbook entry names a failure mode that exists
The scaling text has no numbers: the capacity table sits beside it
Every high-risk component has a threat that names it
Every eval threshold contains a number
Every observability item names a metric, log, trace or alert
The flow fits the latency target: pick faster models, never relax the target

What the shop design ended with

Guardrails: PII input filter, audit log, grounded output filter, action schema check, idempotency check, approval review controls, spend rate limit.

Evals with numbers: grounded accuracy ≥ 0.90 on 300 tickets, PII redaction recall ≥ 0.98, approval coverage = 1.00, p95 ≤ 5.0 s.

A cheaper variant, checked too

The record includes a cheaper variant. Code requires it to lint with no errors or warnings and to cost less per month than the design; otherwise it is a problem to fix.

BoundedUp to 4 fix rounds before each review. A model step that fails or runs out of budget ends the run "Not ready" with the reason; it never crashes it.

The delivered design

A design you can operate, not just a diagram

The Architect's result for the shop, at a private link kept for 7 days, with Markdown and JSON downloads.

Decision record

Context, decision, alternatives with the rule that ruled each out, trade-offs, targets (p95 4.5 s, 99.5% availability), scaling and 7 open risks, each tied to a failure mode.

Rollout and rollback

  • Shadow beside human agents until accuracy and recall meet the thresholds.
  • Canary with the approval gate mandatory.
  • Full while watching cost per ticket and queue depth.

Rollback routes every ticket to people with the gate closed.

Runbook

4 alerts with meaning and first action. Example, duplicate-payment: alert on a second refund proposal for an order with an executed action; hold that order's approvals, cancel the duplicate, check the audit log.

Observability that names signals

Traces per ticket, retrieval scores and cited passage ids, sentences removed by the output filter, schema-check rejections, approval latency and edit distance, redaction counts, cost per ticket.

Threats mapped to OWASP LLM Top 10 (2025)

7 threats: LLM01 prompt injection, LLM02 disclosure, LLM05 output handling, LLM06 excessive agency, LLM08 vector weaknesses, LLM09 misinformation, LLM10 unbounded consumption. Each names its control.

Owner overrides

Every limit and switch can be changed from the owner's private console; each change is stored with a note, and the /admin switch always stops new designs.

Trust boundaries

Three zones, and what may cross

Loading the 3D view.
Amber: /custom calls the Claude API from the browser with the visitor's key, around the server

Browser to server

TLS, HSTS for a year, strict CSP with no inline code, frame-ancestors 'none'. Per-IP limits are spent before validation; bodies over 200 KB and NaN values are refused.

Inside the server

Non-root, read-only filesystem, no capabilities, no-new-privileges, CPU and memory limits. Releases are refused if a hash does not match; nothing unapproved is published. /admin answers 404 without a 16+ character password.

Server to outside

OpenRouter with data collection denied; the run budget is checked before every call. The reviewer sees the design, never the visitor's words. Trust and Radar data are mounted read-only; Ollama is reachable only on the Docker network.

Never reaches the server

The visitor's own key on /custom. Only that page's CSP allows api.anthropic.com; the server builds the prompt and checks the draft, and the page never stores the key.

Failure, testing and operations

Built to fail in a known way

When something breaks

  • A draft still failing the linter after two revisions is stored as rejected; nothing is published.
  • Daily cap or model outage: generation waits; the library is unaffected.
  • A crash restarts the container; leased jobs return; designs in flight are marked failed.
  • Missing Trust or Radar data: empty states and no starters, no errors.
  • Weekly budget nearly used: the brake pauses new designs and generation, with a message.

How it is tested

  • 724 tests on every push; models are scripted fakes.
  • Library evaluation at 1.00; 15 test files for the Architect alone.
  • Architect launch gate: 8 of 8 (100%) on real models before it was switched on.
  • Every bug fix starts with a failing test.

How it is deployed

  • Note the current commit, pull, rebuild with the read-only data mounts.
  • Wait for healthy, check the worker log has no traceback, check /healthz answers 200.
  • Any check fails: check out the noted commit and rebuild.
  • A bad release: point CURRENT back at one of the last 10.
  • Worker heartbeats stop: the uptime monitor marks it down in about 30 minutes.
